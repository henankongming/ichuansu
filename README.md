# ichuansu 项目说明与 AI 开发规格

> **文档用途：** 将本文上传到一个新的 AI 编程会话，作为项目需求基线。  
> **项目名称：** `ichuansu`（易传输）  
> **规格版本：** Go 原生编译版 / MVP  
> **核心目标：** 两台已安装并配置好 Xray 的电脑，使用现有 Xray 通信路径运行同一个 `ichuansu` 程序，互相上传和下载文件。  
> **重要声明：** 本文定义的是目标行为和开发约束；实际 Xray 配置能否承载两端应用之间的直接连接，必须通过配置检查和实机验证，不能仅凭“两边 Xray 都能运行”就认定可达。

---

## 0. 给 AI 编程助手的首要要求

请先完整阅读本文，再开始设计、验证和编写代码。不要擅自改变以下原则：

1. **只开发一个程序 `ichuansu`。** `iget` 和 `iput` 是同一个程序的两个子命令，不是两个独立软件。
2. **使用 Go 语言开发。** 使用 Go 标准库优先，避免要求用户安装 Python、Java、Node.js 或其他语言运行环境。Go 编译器只在开发/构建阶段需要，普通用户运行发布包时不需要安装 Go。
3. **Windows 以 CMD 命令作为用户入口。** 提供 `ichuansu.cmd`，用户在 CMD 中输入 `ichuansu iget ...` 或 `ichuansu iput ...`。为实现 Go 原生程序，Windows 发布包内部会有一个由 Go 编译生成的辅助可执行文件（例如 `_ichuansu.exe`）；用户不需要直接打开或手动操作它。不要把两个命令做成两个 EXE。
4. **Linux 提供一个原生可执行文件** `ichuansu`，在 Terminal 中运行。普通用户不需要安装 Go 运行环境。
5. 两端使用部署环境中已有的 Xray 和 `i.json`。**不得修改、覆盖、重写或自动生成用户的 `i.json`**，也不得更换用户现有的 Xray 协议、加密方式、服务器地址或身份配置。
6. **不增加 VPS、中转服务器、云服务、第三方存储或第三方传输节点。** 目标是使用当前部署中已经存在且经过验证的 Xray 通信路径，实现两台目标电脑之间的直接应用通信。
7. 不要擅自假设哪台电脑是 Xray 客户端/服务端、使用哪个协议、哪个端口或 SOCKS 端口。Xray 网络角色按现有 `i.json` 和实际运行状态决定；应用层的 `iget`/`iput` 请求角色则由每次命令决定。
8. **先验证现有 Xray 路径能否到达对端 `ichuansu` 服务，再开发完整传输功能。** 如果不支持，不得悄悄绕过 Xray 直连公网，也不得改成中转架构；必须报告实际缺少的连接条件。
9. 不需要用户把包含 UUID、密码、私钥、域名或 IP 等敏感信息的 `i.json` 贴到 AI 对话中。配置检查应在用户电脑本地完成，诊断信息必须脱敏。
10. 第一版只实现本文列出的核心功能。不要主动增加 GUI、自动解压、文件同步、远程命令执行、账号管理、复杂参数或其他不必要功能。

## 1. 产品目标与边界

`ichuansu` 是一个跨 Windows/Linux 的命令行文件传输工具。两台电脑均已安装 Xray，并且各自的 `i.json` 已经可以按用户当前网络方案正常运行。

`ichuansu` 只负责：

- 识别本机平台、程序目录和现有 Xray 环境。
- 在本机启动一个轻量级文件接收服务，等待对端请求。
- 通过已经存在并验证可用的 Xray 通信路径连接另一台电脑的 `ichuansu` 服务。
- 读取指定源文件或文件夹。
- 文件夹自动压缩为 ZIP。
- 将文件流传输到对端，或接收对端文件流。
- 检查传输结果并将接收文件保存到接收方程序目录。

`ichuansu` 不负责：

- 替代 Xray 或重新实现 Xray 协议。
- 协商/更改 Xray 使用的协议、加密、身份或服务器配置。
- 新建 VPS、中继服务器或云端服务。
- 修改用户现有 `i.json`。
- 自动解压收到的 ZIP。
- 将文件写入接收端程序目录以外的位置。

## 2. 用户操作：只保留一个程序和两个文件命令

### 2.1 下载：`iget`

命令格式：

```cmd
ichuansu iget <远端文件或文件夹路径>
```

示例：

```cmd
ichuansu iget /home/user/report.pdf
ichuansu iget /home/user/project
```

规则：

- 参数表示**远端电脑文件系统中的源路径**。
- 远端路径是普通文件：直接传输，保存到本机 `ichuansu` 程序目录，文件名保持不变。
- 远端路径是文件夹：由远端电脑自动将文件夹压缩为同名 ZIP，再传输到本机程序目录。例如 `project` 变为 `project.zip`。
- 下载到本地后**不自动解压**。
- 远端临时 ZIP 在成功或失败后都应尽可能清理。

### 2.2 上传：`iput`

命令格式：

```cmd
ichuansu iput <本地文件或文件夹路径>
```

示例：

```cmd
ichuansu iput "C:\Data\report.pdf"
ichuansu iput "C:\Data\project"
ichuansu iput "/home/user/project"
```

规则：

- 参数表示**发起命令的本机文件系统中的源路径**。
- 本地路径是普通文件：直接上传，文件名保持不变。
- 本地路径是文件夹：先在本地临时压缩为同名 ZIP，再上传到远端程序目录。例如 `project` 变为 `project.zip`。
- 远端收到 ZIP 后**不自动解压**。
- 上传完成后清理本地临时 ZIP。

### 2.3 接收文件的保存位置

- `iget` 下载的文件保存在执行 `iget` 的电脑上 `ichuansu` 程序所在目录。
- `iput` 上传的文件保存在接收 `iput` 的电脑上 `ichuansu` 程序所在目录。
- 不增加 `-o`、`--output` 等保存路径参数。
- 保存位置以程序自身所在目录为准，不能以用户打开 CMD/Terminal 时的当前工作目录为准。
- 如果目标目录已经有同名文件，第一版默认拒绝覆盖，显示文件名冲突。

### 2.4 文件名与目录压缩规则

- 普通文件保留源文件名。
- 文件夹压缩后使用文件夹名称加 `.zip`。
- ZIP 内保留该文件夹本身作为顶层目录。例如 `project/a.txt` 在 ZIP 内仍为 `project/a.txt`。
- ZIP 内不能包含磁盘盘符、绝对路径或 `..` 路径段。
- 不跟随指向源文件夹以外位置的符号链接。
- 压缩应在源文件所在电脑完成：`iget` 由远端压缩，`iput` 由本地压缩。
- 临时 ZIP 使用唯一临时文件名，不长期留在源目录或程序目录。
- 不自动解压 ZIP，也不执行上传或下载的文件。

## 3. Go 技术路线与运行环境

### 3.1 语言与依赖

- 使用 **Go** 编写核心程序。
- 优先仅使用 Go 标准库，例如 `net`、`net/http`、`archive/zip`、`crypto/sha256`、`os`、`path/filepath`、`encoding/json` 等。
- 除非有明确技术理由并说明，否则不要引入第三方 Go 依赖。
- Go 编译器只在开发者构建程序时需要。发布给最终用户的程序应为已编译的原生程序，用户无需安装 Go、Python、Java、Node.js 或其他语言运行时。
- Xray 是用户已经安装的独立网络软件，不属于 Go 运行时依赖。

### 3.2 Windows 用户入口

Windows 用户希望通过 CMD 操作，不希望自己直接管理 EXE。因此发布包应提供 CMD 启动入口：

```text
ichuansu.cmd
```

用户输入：

```cmd
ichuansu iget "C:\RemoteData\report.pdf"
ichuansu iput "C:\LocalData\report.pdf"
ichuansu serve
```

`ichuansu.cmd` 将参数原样传递给同目录的 Go 编译程序，并正确返回退出码。Go 编译的内部程序可命名为 `_ichuansu.exe`，由 CMD 脚本调用。用户只需使用 CMD 命令，不需要双击或直接输入内部 EXE 文件名。

**技术事实必须写清楚：** Windows 上 Go 原生编译的程序通常是 `.exe` 文件。CMD 脚本可以作为用户入口、隐藏内部调用细节，但不能把 Go 编译程序变成纯 `.cmd` 脚本。本文选择“CMD 操作入口 + 内部 Go 原生程序”，是兼顾用户体验和免安装运行环境的方式。

建议 Windows 启动器逻辑：

- 使用 `%~dp0` 获取启动器所在目录。
- 调用同目录 `_ichuansu.exe`。
- 使用 `"%~dp0_ichuansu.exe" %*` 一类方式传递参数，并确认包含空格/中文的参数不会被错误拆分。
- 正确传回内部程序的退出码。
- 不调用 Python、PowerShell 作为核心运行时。

### 3.3 Linux 用户入口

Linux 发布包提供单个 Go 原生可执行文件：

```bash
./ichuansu serve
./ichuansu iget /remote/path/report.pdf
./ichuansu iput /local/path/report.pdf
```

文件需要设置可执行权限。Linux 用户不需要安装 Go 运行时。

### 3.4 发布平台

至少构建并测试：

- Windows x86-64（`windows/amd64`）。
- Linux x86-64（`linux/amd64`）。

如构建环境允许，可额外提供 Windows ARM64 和 Linux ARM64，但不是第一版验收前提。不同平台使用各自编译产物，不要让 Windows 程序尝试运行 Linux 二进制，反之亦然。

## 4. 建议目录结构与 Xray 配置位置

建议将 `ichuansu` 放在现有 Xray 程序目录中，方便读取同目录 `i.json`，也让接收文件保存到这个目录。

### Windows

```text
Xray/
├── xray.exe                 # 用户已有
├── i.json                   # 用户已有；ichuansu 只读，不修改
├── ichuansu.cmd             # 用户从 CMD 调用的入口
├── _ichuansu.exe            # Go 编译的内部核心程序
└── （上传/下载收到的文件保存在这里）
```

### Linux

```text
xray/
├── xray                     # 用户已有
├── i.json                   # 用户已有；ichuansu 只读，不修改
├── ichuansu                 # Go 编译的主程序
└── （上传/下载收到的文件保存在这里）
```

要求：

- 保存目录通过程序自身可执行文件/启动器所在目录确定，不使用当前工作目录。
- Windows 从 `ichuansu.cmd` 所在目录定位 `_ichuansu.exe`；核心程序也应能可靠确定它自身所在目录。
- Linux 以 `ichuansu` 可执行文件所在目录作为程序目录。
- `i.json` 位于现有 Xray 配置目录。推荐与 `ichuansu` 放在同一个目录。如果实际安装布局不同，第一版应明确提示找不到配置文件，不得擅自搜索磁盘上多个同名配置并随意选择。
- 不把用户收到的文件放进临时目录；临时传输文件和临时 ZIP 应在系统临时目录或程序目录下受控创建，并在完成后清理。

## 5. 服务运行方式与双端角色

### 5.1 两台电脑都要运行同一个 ichuansu 接收服务

文件传输采用请求方/接收服务方模式。两台电脑都运行同一个程序并开启接收服务，因此任意一方都可以发起 `iget` 或 `iput`。

建议命令：

```cmd
ichuansu serve
```

这条命令在本机启动接收服务并保持运行。用户可在另一个 CMD/Terminal 窗口执行 `iget` 或 `iput`。如果服务没有运行，发起端应在合理超时后提示对端 `ichuansu` 服务未响应。

也可以评估让无参数命令 `ichuansu` 等价于 `ichuansu serve`，但要在帮助信息和 README 中保持一致。不要让 `iget` 或 `iput` 在接收端未运行时假装可以完成传输。

### 5.2 Xray 网络角色与文件传输角色分开

- 哪台电脑在 Xray 层充当客户端或服务端，由现有 `i.json` 和当前运行配置决定。
- 不要求 Xray 客户端角色必须等于文件下载方，也不要求 Xray 服务端角色必须等于文件接收方。
- 在应用层，执行 `iget`/`iput` 的电脑是本次请求方；另一台电脑上的 `ichuansu serve` 是本次响应方。
- A、B 两台电脑都应能发起请求，但必须以实测确认现有 Xray 通信路径支持所需方向。

### 5.3 Xray 进程管理

- 优先复用用户已经启动的 Xray，不要重复启动第二个实例。
- 第一版默认不自动关闭、不重启、不覆盖现有 Xray 进程。
- 如果 Xray 未运行或通道不可用，给出清楚提示；是否提供显式的 `ichuansu xray-start` 等管理命令不属于 MVP，不要擅自增加。
- 不要自行猜测 Xray 启动参数。需要诊断时先检查现有环境，并输出脱敏信息。

## 6. Xray 集成与点对点可行性验证

### 6.1 项目对 Xray 的定位

- Xray 继续负责现有网络通信、代理路由和加密传输。
- `ichuansu` 负责文件服务与文件传输应用逻辑。
- `ichuansu` 不实现 VLESS、VMess、Trojan、Shadowsocks 等 Xray 协议，不复制或替代 Xray 的加密逻辑。
- `ichuansu` 不修改 `i.json`，不改变 Xray 的客户端/服务端角色，不另建任何中转节点。
- 文件数据必须沿用户指定并验证过的现有 Xray 路径传输。不得在 Xray 通道不可用时偷偷改用公网明文直连。

### 6.2 AI 不得作出的未经验证假设

不要未经检查就假设：

- 两台电脑都能连接同一个 Xray 节点，就代表两台电脑能直接访问彼此。
- `i.json` 中出现的 IP/域名一定是对端电脑的应用地址；它也可能是某个 Xray 节点地址。
- Xray 配置一定提供 SOCKS5 入站，或 SOCKS5 一定使用某个常见端口。
- Xray 的代理加密连接会自动把任意应用服务端口映射到另一台电脑。
- 一台电脑能访问另一台电脑，反向也必然可访问。

### 6.3 开发前的最小网络验证

在实现完整文件传输前，先写最小诊断/连通性原型，基于两台真实测试电脑完成：

1. 本机 Xray 是否已按现有 `i.json` 正常运行。
2. 当前配置实际暴露了哪些本地入站接口、出站接口和路由；只输出非敏感字段。
3. 现有配置如何把应用连接送到目标电脑，以及目标电脑如何通过 Xray 接收该连接。
4. A 到 B 的 `ichuansu` 服务端口是否可达；B 到 A 是否可达。
5. 哪个本地地址/端口是 `ichuansu` 应监听或连接的正确入口。
6. 防火墙、NAT、端口监听或 Xray 路由是否阻止应用连接。
7. 通过连接测试或抓包/日志验证文件传输数据确实经过预期 Xray 路径，而非绕过 Xray。

**端点发现要求：** 用户希望命令只有 `iget <远端路径>`，不提供远端 IP、域名或端口参数。因此程序必须能从当前部署中明确确定唯一远端应用端点。这可能来自现有 Xray 配置和已验证的网络约定，但不能只因 JSON 中出现 IP/域名就直接认定。如果配置中无法唯一确定远端 `ichuansu` 服务地址，AI 必须将其列为阻塞条件并说明最少还缺什么信息；不能凭空猜地址，也不要擅自新增用户不想要的复杂命令参数。

**如果网络验证失败：**

- 暂停完整传输功能开发或将其明确标记为未验证。
- 具体说明当前配置缺少哪一段路径、入站、路由或可达性。
- 不得新增 VPS/中继服务。
- 不得擅自修改 `i.json`。
- 不得用绕过 Xray 的直接公网连接冒充目标方案。

## 7. 应用层文件传输设计

Xray 负责网络通道，但不会替 `ichuansu` 自动执行远端文件读取、ZIP 压缩或文件写入。因此两端都需要运行 `ichuansu serve`，并由 `ichuansu` 自己定义最小应用层请求/响应格式。

设计要求：

- 使用简单、可流式处理的协议。优先考虑 HTTP/1.1 风格的文件 API，或简单 TCP 消息格式；选择前先确认它能可靠地承载在现有 Xray 路径上。
- 只实现必要接口：健康检查、下载文件/目录、上传文件。
- 不要为了应用协议再设计一套加密算法；传输加密由现有 Xray 路径负责。
- 请求中明确区分操作、远端源路径、文件名、文件大小和 SHA-256 等元数据。
- 文件内容必须流式传输，不能将整个文件一次性读入内存。
- `iget` 请求由远端服务在远端读取源路径并返回文件流；目录则先压 ZIP 再返回。
- `iput` 请求由发起方发送文件流；远端服务仅把内容写到远端程序目录。
- 健康检查必须验证远端 `ichuansu` 服务本身，不得仅凭 Xray 节点在线或本地 Xray 进程存在就报告远端在线。

### 7.1 接收服务监听

- 服务必须监听在经过网络验证、确实能通过现有 Xray 路径到达的地址和端口。
- 不要默认绑定公网所有网卡（如 `0.0.0.0`）并开放未认证写入接口。
- 如果 Xray 现有配置提供本地代理入口，只有在实际配置与连通性测试证明可用时才能使用；不得硬编码常见 SOCKS 端口。
- 应用端口可以采用明确的默认值，但必须先验证该端口的连接如何通过现有 Xray 路径到达对端；不能把“固定端口”误当作“端口已经可达”。

## 8. 文件服务安全要求

文件服务有读写磁盘的能力，必须限制权限和输入：

1. 上传接收端只能把文件写入接收端 `ichuansu` 程序目录，不能接受客户端指定任意远端保存路径。
2. 下载端只能读取运行 `ichuansu` 的操作系统用户本来就有权限读取的文件；路径必须规范化并进行权限/路径检查。
3. 防止路径穿越、绝对路径注入和文件名伪造。
4. 不覆盖已有文件；除非将来明确增加用户确认机制，否则默认冲突即拒绝。
5. 不执行上传或下载文件，不自动解压 ZIP。
6. 服务不得无保护地暴露在公网。优先只接受现有 Xray 专用路径送达的连接。
7. Xray 的传输加密不自动等同于应用服务授权。若无法确认只有预期对端能访问服务，必须先设计应用层共享密钥/令牌或其他端点认证；不得开放无认证的远程写入服务。不要把令牌放在命令行参数、日志或错误信息中。
8. 日志不得记录 UUID、密码、私钥、认证令牌或其他敏感配置值。
9. 对 ZIP 条目进行规范化，避免归档中出现绝对路径或 `..` 路径段。虽然本项目不解压 ZIP，仍应避免生成不安全归档。
10. 对磁盘空间不足、权限不足、断连、重复文件名等错误给出明确提示。

## 9. 传输可靠性与终端输出

第一版需要：

- 传输前检查源文件/目录存在且有读取权限。
- 显示当前文件名、传输方向、已传输字节数或百分比。
- 使用流式读写，支持大文件。
- 使用 SHA-256 校验传输前后文件内容。
- 接收端先写入唯一临时文件（例如 `.part`），长度及 SHA-256 校验成功后再原子重命名为正式文件。
- 失败时清理不完整临时文件，不得显示为成功。
- 默认拒绝覆盖同名文件。
- 设置合理连接超时、健康检查超时和传输错误处理，避免永久挂起。

成功输出示例：

```text
[ichuansu] 已连接对端文件服务。
[ichuansu] 正在下载 report.pdf
[====================] 100%
[ichuansu] SHA-256 校验通过。
[ichuansu] 下载完成：<ichuansu 程序目录>/report.pdf
```

对端服务不可用输出示例：

```text
[ichuansu] 无法连接对端 ichuansu 服务。
请确认对端电脑已运行 ichuansu serve，并检查现有 Xray 连接。
```

错误区分应尽可能具体：

- 本机 Xray 未运行或本机配置不可用。
- 本机 Xray 通道未就绪。
- 对端应用端点不可达或连接超时。
- 对端电脑可达，但 `ichuansu` 服务未运行。
- 远端源路径不存在或没有读取权限。
- 本地源路径不存在或没有读取权限。
- 接收端目录不可写或磁盘空间不足。
- 同名文件已存在。
- 传输中断或 SHA-256 校验失败。

连接失败时，不要简单断言对方电脑已关机；只能报告当前路径/服务无法响应。

## 10. 命令清单与退出码

第一版至少支持以下命令：

```text
ichuansu serve                         # 启动本机接收服务，前台运行
ichuansu iget <远端文件或文件夹路径>    # 下载到本机程序目录
ichuansu iput <本地文件或文件夹路径>    # 上传到对端程序目录
ichuansu --help                        # 显示帮助
ichuansu --version                     # 显示版本
```

不提供用于指定目标保存目录的参数。不要求用户输入远端 IP/域名/端口；远端应用端点应从已经确认的现有部署连接关系中确定。若无法唯一确定，先报告配置/部署信息不足，不要静默猜测。

建议退出码：

- `0`：成功。
- `1`：一般执行失败。
- `2`：命令或参数错误。
- `3`：本机 Xray/配置/连接入口问题。
- `4`：对端应用服务不可达。
- `5`：源路径不存在、权限不足或路径非法。
- `6`：目标文件名冲突。
- `7`：文件传输校验失败。

Windows CMD 启动器必须把内部 Go 程序的退出码正确返回给 CMD。

## 11. 第一版明确不做的功能

- 不做 GUI。
- 不拆分 `iget` 和 `iput` 为两个程序。
- 不需要用户安装 Python、Java、Node.js 或 Go 运行环境。
- 不把 Python 脚本作为发布版核心程序。
- 不要求用户直接操作内部 `_ichuansu.exe`；Windows 通过 `.cmd` 入口使用。
- 不自动解压 ZIP。
- 不引入 VPS、中转服务器、云存储或第三方服务。
- 不修改 `i.json` 或自动更换 Xray 配置。
- 不实现 Xray 协议或自创传输加密算法。
- 不做文件同步、目录镜像、删除远端文件或远程命令执行。
- 第一版不要求断点续传、多任务并发、压缩等级控制或复杂任务队列。
- 不默认覆盖同名文件。

## 12. MVP 验收标准

只有完成以下测试，才可以称为 MVP 完成。

### A. 单文件下载

- A、B 两台电脑均运行 Xray，且均启动 `ichuansu serve`。
- 在 A 执行 `ichuansu iget <B 上文件绝对路径>`。
- 文件保存到 A 的 `ichuansu` 程序目录。
- 文件名保持不变，SHA-256 与 B 源文件一致。

### B. 文件夹下载

- A 执行 `ichuansu iget <B 上文件夹绝对路径>`。
- A 得到同名 ZIP。
- ZIP 可正常打开，内部保留源文件夹顶层目录结构。
- 不自动解压。

### C. 单文件上传

- A 执行 `ichuansu iput <A 上文件绝对路径>`。
- 文件保存到 B 的 `ichuansu` 程序目录。
- 文件名保持不变，SHA-256 与 A 源文件一致。

### D. 文件夹上传

- A 执行 `ichuansu iput <A 上文件夹绝对路径>`。
- B 得到同名 ZIP。
- ZIP 可正常打开，不自动解压。

### E. 对端服务未运行

- 停止 B 的 `ichuansu serve`。
- A 执行 `iget` 或 `iput`。
- A 在合理超时内收到明确提示，不永久等待。
- 提示不能把“服务未响应”武断等同于“电脑关机”。

### F. 跨平台与路径

- Windows CMD 能调用 `ichuansu.cmd`，不需要安装 Python/Java/Node.js/Go。
- Linux 能运行原生 `ichuansu` 二进制，不需要安装 Go 运行环境。
- 带空格和中文的本地路径可正常使用。
- 从非程序目录执行命令时，接收文件仍保存到程序目录。
- 同名文件存在时拒绝覆盖。

### G. Xray 路径

- 文件数据必须经过用户现有且已验证的 Xray 点对点通信路径。
- 不出现新增 VPS 或中转服务器。
- 不修改 `i.json`。
- 不使用绕过 Xray 的公网直连冒充通过。
- 如果现有配置不能实现应用端点直接互通，报告具体阻塞条件，不得标记网络验收通过。

## 13. 推荐开发顺序

请严格按阶段实施；先验证连接，不要一开始就写完所有功能。

### 阶段 1：Go 项目骨架与环境诊断

- 创建 Go module 和单一 `ichuansu` 命令入口。
- 实现 `--help`、`--version` 和程序目录识别。
- 识别平台对应的 Xray 程序以及同目录 `i.json`。
- 只读解析 Xray 配置，输出脱敏诊断信息；禁止写回配置。
- 确认已有 Xray 进程、入站/出站和可用的现有通信路径。

### 阶段 2：点对点应用连通性验证

- 先实现最小 `serve` 服务和健康检查接口。
- 在两台真实电脑上测试 A 到 B、B 到 A。
- 确认远端端点如何从当前配置/部署关系中唯一确定。
- 确认应用连接确实经过现有 Xray 路径。
- 若不能实现，不要继续声称文件传输可用；先清楚报告缺失条件。

### 阶段 3：普通文件传输

- 实现普通文件 `iget` 和 `iput`。
- 接收端固定写入自身程序目录。
- 实现流式传输、进度、SHA-256、临时文件、原子重命名和冲突保护。

### 阶段 4：文件夹 ZIP

- 实现 `iget` 远端压缩、下载 ZIP。
- 实现 `iput` 本地压缩、上传 ZIP。
- 验证 ZIP 目录结构与路径安全。
- 确认不自动解压，并清理临时 ZIP。

### 阶段 5：跨平台发布与交付

- 构建 Windows 内部 Go 程序 `_ichuansu.exe` 和 `ichuansu.cmd` 启动器。
- 构建 Linux 原生 `ichuansu`。
- 测试 CMD 参数传递、空格、中文、退出码和程序目录定位。
- 编写 README，说明两端如何启动服务和执行上传/下载。
- 列出实际通过的测试、未验证的网络条件和已知限制。

## 15. 一句话核心原则

**ichuansu 是一个 Go 编写的跨平台单程序文件传输工具：Windows 通过 CMD 入口使用，Linux 运行原生二进制；两台电脑都运行同一个接收服务，`iget` 下载远端路径、`iput` 上传本地路径，文件夹自动 ZIP 且永不自动解压，接收结果保存到接收方程序目录；Xray 继续使用现有 `i.json` 负责网络通信，不修改配置、不增加 VPS 或中转服务。**
